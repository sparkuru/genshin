# 数据包路径（公开演示）

状态：本文描述 c/g Prefix NAT、VPS hub 路由、客户端策略路由和 road-warrior 的可复现路径；公开示例中的地址均为演示值，生产验收证据保存在本地 handoff。

## 家庭访问公司

例：家庭 a1 `192.0.2.20` 访问公司主机 `10.92.0.50`。

```text
192.0.2.20 -> 10.92.0.50
        |
        | c：源地址映射为 10.91.0.20，目标保持 10.92.0.50
        v
WG c 10.90.0.2 -> VPS 10.90.0.1 -> g 10.90.0.3
        |
        | g：目标地址映射为真实 192.0.2.50
        v
公司主机 192.0.2.50
```

公司主机看到的源地址应是 `10.91.0.20`，不能是 `192.0.2.20`；否则公司主机会把源地址误判为本地 LAN 并尝试 ARP。

返回路径：

```text
192.0.2.50 -> 10.91.0.20
        |
        | g：源地址映射为 10.92.0.50
        v
VPS -> c
        |
        | c：目标地址映射为真实 192.0.2.20
        v
192.0.2.20
```

同一连接的反向 NAT 由 conntrack 维护；新建连接必须同时覆盖两个方向。

## 公司访问家庭

例：公司主机 `192.0.2.30` 访问家庭 `10.91.0.3`。

```text
192.0.2.30 -> 10.91.0.3
        |
        | g：源地址映射为 10.92.0.30
        v
WG g -> VPS -> c
        |
        | c：目标地址映射为真实 192.0.2.3
        v
家庭主机 192.0.2.3
```

家庭主机看到的源地址应是 `10.92.0.30`。

## 出差客户端

例：a3 使用 `10.93.0.10/32`，访问家庭 `10.91.0.3`：

```text
a3 10.93.0.10 -> VPS 10.90.0.1 -> c 10.90.0.2
                                      |
                                      | c：10.91.0.3 -> 192.0.2.3
                                      v
                              家庭主机 192.0.2.3
```

出差客户端访问公司时使用 `10.92.0.X`，路径对应地送往 g。road-warrior 源地址保持 `10.93.0.X`，不需要把它伪装成家庭或公司地址；c/g 必须经 VPS 具备返回 `10.93.0.0/24` 的路由。

VPS 对每个 road-warrior `/32` 必须同时存在 WireGuard cryptokey peer 和内核返回路由。
只用 `wg syncconf` 动态加入 peer 不会自动创建新 `/32` 路由；当前添加工具会显式执行 `ip route replace <address> dev wg0`，而 `wg-quick@wg0` 重启会从正式配置自动恢复该路由。

## 本地与远端同 host octet

两侧可以同时存在：

```text
本地家庭：192.0.2.3
远端公司：10.92.0.3
```

或者在公司侧：

```text
本地公司：192.0.2.3
远端家庭：10.91.0.3
```

这正是 translated prefix 的作用。

## 必须验证的包级不变量

- VPS 路由表不出现两个真实的 `192.0.2.0/24`。
- c/g 的 LAN 主机收到的跨站点源地址分别属于 `10.91.0.0/24` 或 `10.92.0.0/24`。
- VPN 中断时，本地 `192.0.2.0/24` 和本地互联网仍正常。
- VPN 恢复后，LAN 终端不需要重启即可重新访问 translated prefix。

## 演示验收示例

- `away-test` → `10.91.0.100`：应为 3/3；这验证外出客户端到家庭 translated 前缀。
- `away-test` → `10.92.0.100`：应为 3/3；这验证外出客户端到公司 translated 前缀。
- `home-host` → `10.92.0.100` 与 `company-host` → `10.91.0.100`：各应为 3/3，验证两个站点方向。
- c 的 `NETMAP`、g 的 nft Prefix NAT 计数器均应出现对应流量；VPS 路由表只出现 `10.91`/`10.92`，没有重叠 LAN 的真实路由。
- Docker WireGuard 容器重启后，`wg0`、路由和 iptables 规则应恢复；等待站点 keepalive 收敛后，跨站点测试应再次成功。
- 演示外出客户端 `10.93.0.10` → `10.91.0.3`：可用 ICMP/SSH 验证；测试输出不应把主机名、用户名或 endpoint 写入公开文档。
- 外出客户端的 `/32 dev wg0` 返回路由应在容器重启后自动恢复；首个未完成 handshake 的探测包可能丢失，握手完成后数据面应稳定。
