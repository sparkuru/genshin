# UI/UX Pro Max Frontend Integration

## Goal

Integrate the UI/UX Pro Max skill (UUPM) into a Trellis-managed project when the repository or active task has a frontend/UI surface. UUPM supplies design intelligence and design-system generation; Trellis owns task state, context loading, implementation, verification, and durable project rules.

Do not treat UUPM as a runtime dependency or as a replacement for Trellis. Connect the two through project-local skill initialization, task research, approved design decisions, JSONL context, and UI-aware verification.

## Trigger And Detection

Run this check after Trellis discovery and before frontend planning or implementation.

Classify the repository as frontend/UI when one or more of these are true:

- a manifest contains frontend or mobile UI dependencies such as React, Next.js, Vue, Nuxt, Svelte, Astro, Angular, Solid, React Native, Flutter, SwiftUI, Jetpack Compose, Tailwind, or shadcn/ui
- the repository contains UI source files, routes, templates, stylesheets, assets, or frontend configuration
- package scripts expose frontend commands such as `dev`, `start`, `build`, `storybook`, or `e2e`, and the repository contains corresponding UI code
- the active PRD or task explicitly creates, changes, reviews, or validates a page, screen, component, interaction, visual style, chart, responsive behavior, or accessibility behavior

Do not classify a repository as frontend-only from `package.json` alone. Backend services, CLIs, libraries, and build tooling can use Node without having a UI.

If the task explicitly changes user-facing UI, treat it as a frontend task even when the repository's existing UI footprint is small or not yet established.

## Initialization Check

Initialization means that UUPM has been installed in the current project for the active AI platform. Check the platform-specific project path and verify the generated skill entry point exists. Common paths include:

| Platform | Project-local entry point |
| --- | --- |
| Codex | `.codex/skills/ui-ux-pro-max/SKILL.md` |
| Claude Code | `.claude/skills/ui-ux-pro-max/SKILL.md` |
| OpenCode | `.opencode/skills/ui-ux-pro-max/SKILL.md` |
| Other platforms | the path generated by `uipro init --ai <PLATFORM-NAME>` |

Read the installed UUPM `SKILL.md` to discover its actual `scripts/` and `data/` paths. Treat an installation as incomplete when the entry point exists but the files required by its own instructions are missing. Do not assume a global, home-directory installation satisfies project initialization.

An installation for another AI platform does not satisfy the active platform unless the active platform can load that exact project-local skill. Do not run `uipro init --ai all` to avoid deciding which platform Trellis is using.

## Required User Prompt

When the project is frontend/UI and the active platform has no complete project-local UUPM initialization, stop before UUPM-specific edits or commands and ask exactly one focused question:

```text
A frontend/UI task was detected, but UI/UX Pro Max (UUPM) is not initialized in this project for <PLATFORM-NAME>. Initialize it now with `uipro init --ai <PLATFORM-NAME>`?

Initialization creates the platform-specific UUPM skill files in this project. Choosing no continues the Trellis workflow while skipping UUPM design-system generation and UUPM-specific checks.
```

The prompt must identify the detected platform and the project-local effect. Do not ask this question for backend-only tasks, and do not ask it again when a complete initialization is already present.

If the user declines:

- record `UUPM initialization: declined` in the active plan or task notes when such a task document already exists
- continue the Trellis workflow without UUPM commands
- retain normal frontend validation and human review requirements
- do not create a substitute design-system file that pretends to be UUPM output

If the user accepts, continue with the initialization procedure below.

## Initialization Procedure

1. Confirm the repository root and active AI platform from the current agent/runtime. Use the narrow platform name, such as `codex` or `claude`; do not default to `all`.
2. Prefer the installed `uipro` command when it is available:

   ```bash
   uipro init --ai <PLATFORM-NAME>
   ```

   Otherwise use the official CLI through `npx`:

   ```bash
   npx uipro-cli@latest init --ai <PLATFORM-NAME>
   ```

   Use `--force` only when repairing an incomplete installation after telling the user which files will be replaced. Use `--offline` only when network access is unavailable and the CLI's bundled assets are known to be available.
3. Inspect the resulting diff before continuing. Preserve unrelated user changes and do not overwrite an existing platform skill without the user's approval.
4. Verify the generated UUPM entry point and the script/data paths referenced by its instructions. When `scripts/search.py` exists, run its cheapest help/version check before generating design material:

   ```bash
   python3 <UUPM-SKILL-DIRECTORY>/scripts/search.py --help
   ```

If initialization fails, report the exact command, failure, and files created. Do not continue as though UUPM were initialized.

## Trellis Workflow Integration

After initialization, add a short `Trellis Plus: UUPM integration` pointer to the narrowest available durable target:

1. `.trellis/workflow.md` for shared phase behavior
2. a project plan/brainstorm skill for planning behavior
3. a before-dev skill for initialization and execution readiness
4. a check skill for UI verification
5. an update-spec skill for promoting stable UI rules

Do not duplicate the full procedure in every target. Keep the detailed rules in this reference and add phase-specific pointers.

### Plan

For every frontend task whose scope affects user-visible UI:

1. Load the initialized UUPM skill and the relevant frontend specs.
2. Generate a task-specific design system before implementation. Use UUPM's `--design-system` flow and include the detected product domain, visual direction, and technology stack.
3. Save raw UUPM output under the active task's research directory, for example:

   ```text
   .trellis/tasks/<TASK-ID>/research/ui-ux-pro-max.md
   ```

4. Convert selected decisions, constraints, states, and acceptance criteria into `<TASK-DIRECTORY>/design.md`. `design.md` is the approved task decision record, not a dump of search results.
5. Define responsive behavior, loading, empty, error, disabled, success, keyboard, reduced-motion, and accessibility expectations before implementation.

Example command shape, adapted to the installed UUPM path and detected stack:

```bash
python3 <UUPM-SKILL-DIRECTORY>/scripts/search.py \
  "<PRODUCT-DOMAIN> <VISUAL-DIRECTION> <INFORMATION-DENSITY>" \
  --design-system \
  --stack <TECHNOLOGY-STACK> \
  -p "<PROJECT-OR-FEATURE-NAME>" \
  -f markdown \
  > "$TASK_DIR/research/ui-ux-pro-max.md"
```

Do not hard-code a product domain, stack, palette, or style from this example.

### Context Injection

Add the approved design artifact and relevant frontend specs to both implementation and check context. Prefer Trellis's existing context command and preserve its argument order, for example:

```bash
./.trellis/scripts/task.py add-context \
  "$TASK_DIR" implement \
  "$TASK_DIR/research/ui-ux-pro-max.md" \
  "Approved UUPM design research and page rules for this task"

./.trellis/scripts/task.py add-context \
  "$TASK_DIR" check \
  "$TASK_DIR/research/ui-ux-pro-max.md" \
  "Check UI, responsive behavior, and accessibility against the approved UUPM design rules"
```

Add `design.md` and the relevant `.trellis/spec/frontend/` entry point in the same way when they exist. Do not add arbitrary source files to JSONL context just to make the UI agent see them.

### Implement

The implementation agent must read the task's approved design decisions, UUPM research, and relevant frontend specs before changing UI. It may resolve implementation details, but it must not silently replace approved visual or interaction decisions. If a decision is invalidated by technical constraints, record the change in `design.md` and update implementation and check context together.

### Check

The check agent must verify the implementation against both the task acceptance criteria and the approved UUPM decisions. At minimum inspect:

- responsive behavior at the project's supported breakpoints and narrow mobile width
- typography, spacing, color contrast, focus states, keyboard navigation, and accessible names
- loading, empty, error, disabled, success, and permission states
- touch target size and interaction feedback
- reduced-motion behavior and animation restraint
- chart readability and non-color indicators when data visualization exists
- page performance, image handling, large-list strategy, and stack-specific conventions

Lint, type-check, unit tests, and build success are not sufficient UI verification. For browser-automatable web UI work, follow the Playwright automated validation enhancement before asking for manual review. Use device or manual checks only for residual risks that Playwright cannot test effectively, then feed those residual risks into the submit-ready human review gate.

### Update Spec

After verification, promote only stable, reusable UI rules into the project's existing `.trellis/spec/` frontend entry point. Keep task-specific decisions and raw UUPM research in the task. Maintain one project-level source of truth for approved design-system rules; do not create a competing editable `MASTER.md` unless the project already treats it as canonical.

## Verification After Injection

After applying this enhancement, verify:

- frontend detection cites concrete repository or task evidence
- the initialization prompt appears only for a frontend/UI project lacking active-platform UUPM
- user acceptance runs the narrow platform-specific initializer and user decline skips UUPM commands
- incomplete initialization is not reported as successful
- the workflow points to UUPM in Plan, Implement, Check, and Update Spec at the narrowest available targets
- UUPM research is saved under the active task and added to both implement and check context
- UI checks include states, responsive behavior, accessibility, Playwright validation when browser-automatable, and manual review only when needed
- `trellis update` recovery re-applies pointers without silently reinstalling or overwriting UUPM
