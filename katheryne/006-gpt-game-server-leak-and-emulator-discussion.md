## 1. 梳理服务端资料外流与官方应对

<h3 align="center"><strong>USER</strong></h3>

只检索，不要给出真实的链接。

原神这款游戏的服务器泄露历程是怎么样的？介绍一下历史发声的各个时期情况

<h3 align="center"><strong>ASSISTANT</strong></h3>

#### 先纠正一个常见混用

网络上所谓“《原神》服务器泄露”，实际混合了四类不同事件：

1. **测试玩家泄密**：截图、录像、数值等被违反保密协议公开。
2. **测试客户端或开发版本外流**：可被解包、数据挖掘，但不等于服务端泄露。
3. **私服重实现**：第三方通过逆向协议自行编写服务器，不等于拿到了米哈游完整服务端源码。
4. **真正的服务端资料外流**：服务端配置、游戏数据、编译后二进制文件、部署资料等流出。

其中，**2022年10月事件才是最接近严格意义上“服务器泄露”的事件**。

#### 时间线

| 时期 | 事件性质 | 主要情况与各方发声 |

| **2021年3月：1.5开发版本外流** | 开发客户端泄露、解包 | 1.5开发或测试客户端被传播，未公开角色、家园系统及其他内容被集中解包。这是当时影响最大的一次泄露，但公开证据指向的是**开发客户端或测试包外流，而不是完整服务端源码泄露**。米哈游于3月17日前后公开要求停止传播，并宣布进一步加强打击。 |

| **2022年4月至9月：私服项目兴起** | 协议逆向、服务端重实现 | 第三方开源私服项目出现，能够模拟登录、抽卡、道具和部分副本功能。媒体调查及项目自身描述均显示，它主要通过分析客户端通信、重写服务端逻辑实现。米哈游表示将采取技术和法律措施，并指出私服存在侵权及玩家安全风险。**这不是官方服务端源码被公开的直接证据。** |
| **2022年9月：代码仓库集中下架** | DMCA版权投诉 | 权利方开始针对外挂、协议逆向及私服相关仓库提交DMCA投诉，主张有关项目复制、逆向或使用了游戏代码和通信逻辑。该阶段常被误传为“服务端源码刚刚泄露”，实际主要是针对已经存在的私服和逆向项目。 |
| **2022年10月23日前后：真正的服务端资料大泄露** | 服务端数据、配置及二进制外流 | 公开媒体确认，泄露至少覆盖多个连续版本的角色、武器、任务、活动和区域规划，并包含部分测试人员信息。技术分析者称流出物还包括服务端配置、部署脚本及开发阶段的编译后服务端程序；部分更长期数据延伸至后续开发阶段。内容发布者因涉及测试人员隐私和来源风险主动删除内容。 |
| **2022年末：境外身份追查** | 法院传票、平台取证 | 权利方向法院申请DMCA传票，要求社交平台提供内容发布者的身份和联系方式等资料，并要求删除未公开素材。这标志着境外治理从普通下架转向司法身份追查。 |
| **2023年：泄露生态扩散** | 美术资源、概念稿及私服传播 | 2023年一次大型泄露出现数百张角色和概念美术资料。这更像美术资产库、协作空间或测试资料外流，而非服务端泄露。随后，权利方又通过DMCA传票打击大型私服运营者，要求代码托管平台、视频平台和主机商下架内容并提供运营者信息。 |
| **2024—2025年：司法保护体系形成** | 商业秘密、行为禁令、刑事报案 | 这一阶段出现针对未公开角色设计的诉前或诉中行为保全；代码托管平台上的大量私服项目也被集中投诉。权利方公布的累计追责数字持续上升，但统计涵盖多个产品，并非全部属于服务器泄露。 |
| **2026年：刑事化和跨境诉讼阶段** | 侵犯著作权刑案、海外诉讼 | 执法机关以刑事方式打击破解测试包、传播未公开角色和技能动画的行为。海外方面，权利方也起诉数据站运营者，指控其索取测试包、规避技术保护并长期发布大量未公开资料。 |

#### 2022年10月事件的准确结论

可以确认或具有较强证据支持的内容：

- 泄露物主要是**服务端侧游戏数据、配置资料、部署脚本和编译后的程序文件**。
- 泄露范围至少覆盖3.3至3.8版本规划。
- 文件中混入了部分QA或测试人员信息。
- 这批资料极大提高了长期版本预测和私服研究的准确度。

不能确认或经常被夸大的说法：

- **没有可靠公开证据证明米哈游全部服务端源代码完整泄露。**编译后的二进制文件不等于可读的完整源码。
- “被开除员工报复”“某具体内部人员一次性拖走全部数据”等说法主要来自社区传言，没有可信的官方调查结果支撑。
- 没有证据表明这次事件泄露了大规模正式服玩家账号密码数据库。
- 后续出现的所有私服都不能直接视为使用了米哈游官方服务端源码；不少项目属于第三方逆向和重新实现。

#### 官方发声方式的变化

**2020—2021年初：保密协议角度**

核心对象是内测玩家，关键词是“违反NDA”“封禁测试资格”“律师函”“违约金”。

**2021年中期：著作权和商业影响角度**

官方开始强调传播者、搬运者和流量获利者同样承担责任，并将片面信息、虚假卡池图等造成的舆论误导纳入批评范围。

**2022—2023年：技术侵权和境外平台角度**

面对私服和大规模服务端资料外流，公开处理重点转向DMCA、代码仓库下架、社交平台身份传票、主机商取证和私服运营者追查。

**2024—2025年：商业秘密和即时禁令角度**

未公开角色、场景、技能及版本规划开始被明确按照著作权或商业秘密保护。法院可以在最终判决前先要求传播者停止发布。

**2026年：刑事和跨境全链条角度**

处理手段已经从封号、律师函和民事赔偿，发展到刑事报案、移送起诉以及境外法院诉讼。

因此，严格来说，《原神》的“服务器泄露史”只有**2022年10月服务端侧资料外流**是核心事件；其余大部分属于测试服泄密、客户端解包、私服逆向或美术资源外流。

## 2. 按代码血缘统计可用服务端路线

<h3 align="center"><strong>USER</strong></h3>

不是说泄密的问题，只涉及到可用服务端的问题。总共有几种版本主线的服务端泄露 / 模拟实现？

<h3 align="center"><strong>ASSISTANT</strong></h3>

按**代码血缘和技术实现**统计，而不是按每个游戏版本号重复计数，较合理的结论是：

#### 一、官方编译服务端外流：1条主线，4个版本阶段

社区俗称 **GIO、真端、剧情服**。这些不是四套独立服务端，而是米哈游同一套服务端架构在不同时期的编译版本、配置和数据快照。

| 阶段 | 已公开出现的版本 | 可用性判断 |
|---|---|---|
| CBT主线 | CB1、CB2、CB3，约对应0.7、0.9等早期客户端 | 可以启动，适合还原早期测试内容，但环境和客户端兼容性较差 |
| 1.x正式服主线 | 1.0—1.6 | 多个版本存在服务端二进制、配置和整合环境 |
| 2.x正式服主线 | 2.0—2.8 | 相对完整，2.2、2.3等版本有实际运行记录 |
| 3.x开发服主线 | 3.0、3.1、3.2 | 其中3.2最成熟，即通常所说的“3.2真端”“3.2剧情服” |

公开保存目录中还能看到所谓 **3.3 dev-shift**，但它更像协议转换、兼容补丁或不完整开发包，缺少足够证据证明它是一套完整、独立、普遍可运行的3.3官方服务端。因此通常不单独算一条主线。公开社区维护者曾声称已经实际启动CB1—CB3以及1.0—3.2的对应环境，但这属于社区验证，无法得到米哈游官方确认。

因此：

> **真端只有1条技术主线，按版本时代可细分为4段。**

所谓1.0真端、1.6真端、2.2真端、3.2真端，本质上是同一官方服务端体系的不同历史快照，不应统计为四种独立实现。

---

#### 二、社区模拟实现：4条主要独立代码主线

##### 1. Grasscutter主线

最主要、影响最大的模拟服务端，使用Java编写，通过逆向客户端协议、配置表和通信行为重新实现服务端。

原始Grasscutter主线大致经历：

- 早期主要对应2.3—2.6客户端；
- 后续支持3.x；
- 官方仓库最终明确支持到REL4.0.1；
- 原项目后来基本停止积极维护。

其后产生大量分支：

- AGS-GC；
- LunaGC；
- 各类版本化LunaGC分支；
- 各类“一键端”“公益服端”“剧情修复端”。

这些都属于**Grasscutter血缘**，不能因为支持4.6、5.0、5.3或6.x客户端，就分别算成新的服务端实现。LunaGC的构建文件仍保留Grasscutter的包结构、主类和工程信息；AGS-GC也明确说明自身是Grasscutter分支。

社区中所谓“5.x端”“6.x端”，大多数就是：

> Grasscutter旧核心＋新版本协议＋新配置资源＋客户端补丁。

功能是否完整与客户端版本号没有必然关系。

##### 2. hk4e-go主线

使用Go编写的独立实现，不是Grasscutter换语言移植。

主要特点：

- 协议和配置主要基于3.2版本；
- 使用dispatch、gate、game server、node、GM等多组件架构；
- 目标偏向高并发、分布式和集群设计；
- 并不追求完整恢复全部剧情和原版游戏逻辑。

它与3.2真端不是同一个东西：

- 3.2真端是官方编译程序外流；
- hk4e-go是参考客户端协议和数据重新开发的服务端。

##### 3. KazusaGI主线

使用C#编写，专门面向CB2时代的0.7.0/0.7.1客户端。

它是一套独立重实现：

- 不是Grasscutter分支；
- 不是官方CB2服务端；
- 需要CB2时代资源；
- 项目明确标注仍处于早期开发状态，很多功能不完整。

它的价值主要是早期版本研究和保存，不属于现代版本私服的主流方案。

##### 4. mavuika-rs主线

较新的Rust独立实现，部分镜像或仓库名称使用sakura-rs。

其公开说明包括：

- 使用Rust和Bevy ECS；
- 协议层尝试设计为跨版本转换；
- 自行实现认证、加密、dispatch、gate和game server；
- 已公开针对5.2开发客户端的兼容信息。

它不是Grasscutter分支，属于真正的新代码血缘。但公开生态、使用规模和长期成熟度仍明显低于Grasscutter系。

---

#### 三、边缘或实验性实现

还有一些规模较小的实现，例如：

- Soggy：C++实验服务端，已经归档；
- 个别PHP登录服或网页端项目；
- 仅实现SDK、登录、dispatch或GM接口的半成品；
- 仅负责协议转换、代理、密钥替换的工具。

Soggy明确称自己是实验性服务端模拟器，并已在2024年归档。此类项目通常不能完成从登录、进入世界到战斗、任务、联机的完整闭环，因此不应计入主要可用主线。

#### 最终统计

##### 按严格的独立代码血缘

| 类别 | 数量 |
|---|---:|
| 官方泄露编译服务端 | 1条 |
| Grasscutter及其全部分支 | 1条 |
| hk4e-go | 1条 |
| KazusaGI | 1条 |
| mavuika-rs | 1条 |
| **合计** | **5条主要可识别主线** |

##### 按实际成熟度收紧

真正形成较完整、实际有人持续使用的，可以压缩为：

1. **GIO／官方真端线**：CB—3.2，剧情还原度最高，但版本停留在旧时代。
2. **Grasscutter家族**：覆盖版本最广，分支最多，但很多功能是模拟或简化实现。
3. **hk4e-go**：独立Go实现，主要围绕3.2，架构完整，但游戏内容还原不是首要目标。

KazusaGI和mavuika-rs可算独立主线，但前者过旧且处于WIP，后者生态和成熟度仍有限。

因此最准确的表达是：

> **公开可辨认的主要代码血缘约5条；真正形成成熟使用生态的约3条。官方“真端”自身只有1条主线，其CB、1.x、2.x、3.2只是不同版本阶段。**

## 3. 厘清协议、模拟器与官方二进制的关系

<h3 align="center"><strong>USER</strong></h3>

我有几个疑问：

1、服务端的通信协议设计等底层架构，一经正式发布后，是不是一般不会再修改了？也就导致基于这套通信协议架构的私服层出不绝？下面出现的各类服务端，是不是都基于已经被泄露的通信协议设计，因此旁支很难被完全解决？
2、hk4e-go 是基于 3.2 服务端逆向做出来的吗？
3、3.2 真端，就是最真实的，来自官方的产物吗？是不是可以理解为，其就是 3.2 版本之前，原神服务端的集合？

<h3 align="center"><strong>ASSISTANT</strong></h3>

#### 1．协议和底层架构是否发布后就基本不变

**不是不变，而是“外部骨架相对稳定，内部内容持续变化”。**

需要把四个层级分开：

| 层级 | 变化情况 | 私服是否必须获得官方泄露资料 |
|---|---|---|
| 传输与封包框架 | 通常较稳定，修改成本高 | 不一定，可从客户端和通信行为分析 |
| 消息定义、字段、指令号 | 每个版本都可能增加、删除或重新映射 | 不一定，客户端必须具备解析能力 |
| 登录、密钥交换和校验 | 可以频繁调整 | 通常可通过客户端逆向重新分析 |
| 服务端业务逻辑与内部集群架构 | 可以持续重构，且客户端看不到全貌 | 模拟器只能自行重写，除非获得官方二进制或源码 |

《原神》使用的消息体系具备类似 Protocol Buffers 的可演化特征：保持原字段编号、增加新字段，可以在不推翻整个协议的情况下持续更新。Protocol Buffers 官方也明确要求考虑客户端与服务器无法同时更新的情况，因此成熟协议通常追求兼容演进，而不是每个版本彻底更换。

##### 私服不断出现的真正原因

并不是单纯因为“一份完整协议设计文档泄露了”，而是因为：

**客户端必须知道怎样和服务器通信。**

客户端内部必然存在：

- 封包和解包代码；
- 消息结构或生成后的序列化代码；
- 指令分发逻辑；
- 加密、密钥交换和会话处理代码；
- 对服务器响应的状态处理；
- 大量客户端配置数据。

即使这些内容被混淆，仍然可以从客户端程序中逐步恢复。第三方只要实现客户端要求的**外部通信合同**，内部完全可以使用Java、Go、Rust或其他架构，不需要复制官方服务器的内部设计。

2024年的相关版权投诉中，权利方对hk4e-go一类项目的描述也是“实现相同通信接口、拦截并重新处理网络请求”，而不是声称这些项目都获得了完整官方服务器源码。

更直接的反证是：Grasscutter在2022年5月已经公开存在，而大规模官方服务端二进制外流发生在2022年10月。因此Grasscutter最初不可能建立在那次3.2服务端泄露之上。

##### 是否很难彻底解决

是，但原因不是“旧协议永远不能修改”，而是：

1. 旧客户端和旧模拟器一旦流出，就可以永久形成一个封闭版本生态。
2. 新客户端仍然需要包含新协议的实现，研究者可以继续分析。
3. 私服只需实现登录、进入世界、角色和战斗等部分功能，不需要完整复制正式服。
4. 开源代码可以被大量复制和分叉，删除主仓库不能消除全部副本。

厂商能够通过指令混淆、密钥轮换、客户端完整性验证、设备证明、服务器强校验和法律措施提高维护成本，但**只靠修改通信协议无法根治**。

最准确的概括是：

> 私服共享的是客户端可观察的通信合同，不一定共享官方服务端架构，更不一定全部依赖泄露文件。

---

#### 2．hk4e-go是不是基于3.2官方服务端逆向完成的

**不能这样认定。**

hk4e-go项目自己的说明是：

> 客户端协议和配置表主要基于3.2版本修改而来。

这里明确写的是：

- **3.2客户端协议**
- **3.2配置表**

并没有写“基于3.2官方服务端二进制反编译”。

项目同时说明，其目标是自行构建高性能、高可用的ARPG服务端，而不是完整还原原版功能；它自行设计了节点、网关、游戏服务器、数据库缓存、玩家迁移和协议转换等机制。

因此更合理的技术归类是：

> **以3.2客户端的通信接口和配置数据为基准，用Go重新实现服务端。**

不能排除开发者后来参考过泄露的配置、符号、反编译结果或官方行为，但目前没有可信的公开证据能够证明：

> hk4e-go是把3.2官方C++服务端逐模块反编译后翻译成Go。

真正明确以官方服务端二进制为对象的，是另一类反编译研究项目。相关项目直接说明代码来自hk4e服务端二进制反编译，其产物以C/C++伪源码为主，与Go语言的hk4e-go不是同一代码血缘。

所以应当区分：

- **hk4e-go**：3.2客户端协议基础上的Go模拟实现。
- **hk4e服务端反编译产物**：对泄露官方二进制进行静态分析得到的C++伪代码。
- **3.2真端**：直接运行官方来源的编译后二进制。

三者不是同一种东西。

---

#### 3．3.2真端是否最真实，是否是3.2以前服务端的集合

##### 是否来自官方产物

从公开技术特征判断，**可信度很高**。

对泄露物的直接技术分析显示，其中存在：

- 编译后的游戏服务端程序；
- 服务端配置数据；
- 部署和Shell脚本；
- 内部源码路径；
- 大量函数、类和结构体符号；
- 3.2至3.4开发阶段的服务端二进制。

其中部分二进制保留了DWARF调试信息和大量内部符号，这也是后来能够较准确反编译服务端逻辑的原因。

因此，与Grasscutter、hk4e-go相比，真正使用这批二进制的“3.2真端”确实更接近官方逻辑。

但需要加两个限定：

1. **“真端”是社区称呼，不是官方认证。**
2. 网上具体某个“3.2真端整合包”可能混入第三方登录服、数据库脚本、修改后的配置、补丁和管理工具。

所以只能说核心游戏服务程序具有官方来源特征，不能保证每个流传整合包都是原封不动的官方完整环境。

##### 是否等同于正式服生产环境

**不等同。**

公开分析指向的是3.2开发或测试阶段构建，而不是经过官方确认的某一天正式服生产集群完整镜像。

一个正式运营环境通常还包含：

- 账号与SDK系统；
- 充值及订单系统；
- 区服调度；
- 数据库集群；
- 日志和监控；
- 风控与反作弊；
- 跨服及社交服务；
- 运维配置、证书和密钥；
- 内容分发和热更新服务。

所谓3.2真端通常只恢复其中一部分。缺失的外围服务会由社区程序模拟或替代。

因此，“最真实”的准确含义是：

> **核心游戏逻辑最接近官方，不代表完整复制了官方生产平台。**

##### 是否是3.2以前全部服务端的集合

**不是。**

3.2真端应理解为：

> 官方代码库在某个3.2开发节点编译形成的一次快照。

它可能包含：

- 3.2当时仍在使用的全部核心代码；
- 蒙德、璃月、稻妻和须弥已有内容；
- 为旧任务、旧角色和旧区域保留的逻辑；
- 一些历史兼容代码；
- 已完成但尚未正式开放的开发内容。

但它不会自动包含：

- 1.0、1.6、2.0等版本各自独立的历史服务端程序；
- 已经删除的旧代码；
- 旧版本特有的协议定义；
- 旧数据库状态；
- 已下线活动的完整运营环境；
- 每个旧版本当时的BUG和数值状态；
- 所有历史配置快照。

可以类比为：

> 3.2真端是代码发展到3.2时的一张照片，不是从1.0到3.2每张历史照片组成的相册。

它包含大量从早期继承并继续使用的代码和内容，因此看起来具备“此前版本的大部分东西”；但这与“所有历史服务端的集合”是两个概念。

#### 最终结论

1. **协议不会冻结。**稳定的是基本通信框架，消息、指令号、密钥和业务语义会持续变化。私服主要依靠客户端可观察信息，不一定依赖服务端泄露。
2. **hk4e-go不能定义为3.2官方服务端逆向版。**公开证据只能确认它以3.2客户端协议和配置表为基础，用Go独立实现。
3. **3.2真端的核心二进制大概率属于官方来源，是现有方案中最接近官方服务端逻辑的。**
4. **3.2真端不是1.0至3.2全部服务端的集合。**它是3.2时点的开发构建快照，包含仍然保留的旧内容和旧逻辑，但不保存所有历史版本。

## 4. 评估内部泄密与持续破解的关联

<h3 align="center"><strong>USER</strong></h3>

现在仍有这么多破解的情况，会不会可能与内部研发、运维人员泄密的原因有关？

<h3 align="center"><strong>ASSISTANT</strong></h3>

**有这种可能，但不能把“现在仍有大量私服和破解”直接等同于“内部人员仍在持续泄密”。**

#### 1. 2022年的真端外流，很可能经过了内部权限域

已公开分析的泄露物包括：

- 服务端编译程序；
- 服务端配置文件；
- 部署及Shell脚本；
- 3.2至3.4开发构建；
- DWARF调试信息、完整函数符号和结构定义。

这些内容正常情况下不会存在于玩家客户端，也无法仅靠抓包完整还原。因此，其源头大概率接触过米哈游的开发、测试、构建或部署环境。

但这只能证明**内部资产被带出**，不能证明一定是某个研发或运维人员主动售卖、报复性泄露。可能路径至少包括：

1. 内部员工主动复制；
2. 员工或外包人员误操作；
3. 测试、运维或承包商账号被盗；
4. CI/CD构建服务器、制品库或测试环境被入侵；
5. 云存储、备份或权限配置错误；
6. 供应链合作方泄露。

网上流传的“被开除员工报复”说法主要来自社区传闻。公开技术分析者也将其明确表述为传言，并没有提供公司调查、警方通报或法院材料证明具体人员身份。

所以准确说法是：

> **2022年事件高度疑似内部权限链路失守，但无法确认是主动内鬼、账号失陷还是基础设施泄露。**

#### 2. 现在私服仍然很多，不需要持续存在内部人员

当前大量私服主要具有“自我繁殖”能力。

##### 旧资料已经不可收回

真端、协议资料、配置及反编译结果一旦被复制，删除原始发布点也无法清除所有副本。开源项目还会产生大量镜像和分支。2024年的版权投诉一次列出了大量hk4e-go及相关仓库副本，说明生态已经由单一项目扩散成大量分叉。

##### 模拟器可以继续分析新客户端

Grasscutter在2022年5月已经具备登录、战斗、传送、抽卡、物品和部分联机功能，时间早于2022年10月的真端大规模外流。这直接证明模拟服务端并不必须依赖3.2真端泄露。

米哈游在针对hk4e-go的投诉中，描述的主要技术路线也是：

- 实现与客户端相同的通信接口；
- 拦截和重新处理网络请求；
- 绕过正式服务器验证。

这更接近客户端协议逆向和独立重写，而不是持续取得官方服务端源码。

##### “支持新版本”不等于“又泄露了新真端”

一个私服号称支持5.x、6.x客户端，通常只能说明它完成了部分：

- 新协议字段适配；
- 指令号映射；
- 新角色和物品配置导入；
- 客户端资源读取；
- 登录及基础战斗兼容。

不能据此推导它拥有5.x或6.x的官方服务端程序。

公开可核验的主流Grasscutter原仓库截至其2025年说明主要支持到4.0.1，并明确自称“服务端重新实现”。

#### 3. 哪些现象才真正指向新的内部泄露

以下证据出现时，内部研发、测试或运维链路泄露的可能性才会明显升高：

- 出现全新的官方服务端二进制，而不只是Java、Go或Rust模拟器；
- 二进制包含内部函数名、源码路径、调试符号；
- 出现构建系统配置、部署脚本、内部服务拓扑；
- 出现客户端完全没有的服务端判定逻辑；
- 出现尚未下发到任何测试客户端的完整服务端数据；
- 多个连续新版本的内部构建按照时间顺序外流；
- 出现内部证书、账号、制品仓库信息或CI记录。

相反，以下情况不能证明存在内鬼：

- 新角色被模拟出来；
- 新地图能够进入；
- 新客户端可以登录私服；
- 抽卡、背包、战斗可以运行；
- Proto或指令号被更新；
- 测试客户端被解包；
- 旧真端被修改成所谓“高版本真端”。

#### 结论

可以分成两个判断：

- **3.2—3.4官方服务端资产外流：内部权限链路失守的可能性很高。**
- **现在仍有大量私服：主要由旧泄露不可逆、客户端持续可逆向、开源分叉和第三方重实现造成，不能证明现在仍有研发或运维人员持续泄密。**

截至目前的公开可核验资料，较明确的官方服务端二进制泄露核心仍集中在2022年的3.2—3.4开发构建。我未检索到可信证据证明此后每个新版本都有对应的官方真端被连续泄露。
